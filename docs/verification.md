# 検証結果：Nuxt SSR表示差異デバッグ演習

## 実行環境

演習プロジェクトはNuxt 4.5.2で起動し、Node.jsのタイムゾーンを`UTC`に固定してSSRを実行した。ブラウザ側は実行環境のタイムゾーンを用いる。固定した瞬間は`2026-08-01T09:00:00.000Z`である。

| 確認項目 | 実行内容 | 結果 |
| --- | --- | --- |
| 表示差異の単体テスト | `pnpm test` | 成功。UTCとAsia/Tokyoで同一瞬間の表示文字列が異なることを確認した。 |
| 型検査 | `pnpm typecheck` | 成功。Nuxt/Vueの型検査を通過した。 |
| 本番ビルド | `pnpm build` | 成功。NitroのNodeサーバービルドを生成した。 |
| バグありのSSR HTML | `curl http://127.0.0.1:3000/buggy` | 画面の日時は`09:00 UTC`として出力された。 |
| バグありの最終DOM | ブラウザで`/buggy`を表示 | 同じ箇所が`18:00 JST`として表示された。 |
| 修正後のSSR HTML | `curl http://127.0.0.1:3000/fixed` | 初期表示の日時箇所はすべて`ブラウザ時刻を取得中…`だった。 |
| 修正後の最終DOM | ブラウザで`/fixed`を表示 | マウント後にブラウザ環境のタイムゾーンで更新された。 |

## 比較結論

バグあり画面では、サーバーHTMLの`2026年8月1日 09:00 UTC`と、ブラウザが初回Hydrationで期待する`2026年8月1日 18:00 JST`が一致しない。修正画面では、両者が`ブラウザ時刻を取得中…`から開始するため、Hydrationの比較対象が一致する。

ブラウザ固有の時刻表示を初期HTMLへ埋め込む必要があるかどうかは要件次第である。今回の要件は「利用者のローカル時刻を表示する」ことなので、初期値をプレースホルダーにし、`onMounted`後に更新する設計を選んだ。
